# RW04 WebRTC 源码探针

Windows H.264 PeerConnection 探针用独立的 Media Foundation 编码和解码工厂，通过本机 ICE/DTLS 发送合成画面。固定 128×96、单层 constrained-baseline level 1.3、packetization-mode=1，分别核对实际 SDP 和编码 SPS。两次连接验证远端解码亮度、旧连接关闭和新 ICE 凭据，同时报告实际 MFT 编解码回调及实例释放次数。实际窗口采集和双机观看留待后续验证。

Windows H.264 RTP 探针将系统 Media Foundation 编码输出交给固定 WebRTC 的分包器。接收端从实际 RTP 字节经 WebRTC 解包和参数集跟踪器重建 Annex B，独立 Media Foundation 解码器只接受收到的数据。12 帧覆盖 SPS/PPS/IDR、后续非 IDR 帧、变化亮度、尺寸和 RTP 时间戳回绕。64 字节的 payload 上限强制触发 FU-A，最终检查实际分片计数。发送端在样本缺参数集时，从编码器提取并随首个访问单元发送。接收器按收到的参数集初始化媒体内容。

Actions 从固定的 WebRTC 和 depot_tools 提交同步源码及 DEPS，构建一个最小的 VideoFrame 探针。程序生成 I420 测试帧，从 WebRTC API 读回尺寸、采样时间和回绕前后的 RTP 时间戳。两个平台分别上传源码、DEPS 和许可证文件的 Git 标识，以及构建参数和探针结果。仓库只保存探针和配置。

macOS 再从独立 C 文件跨过固定布局的 ABI，使用 WebRTC 的 VideoToolbox H.264 工厂对合成关键帧做本机编解码。保留单帧回归，并在同一组编解码器中验证 18 帧连续流。检查原始尺寸、亮度、关键帧与后续帧、同一会话内 RTP 回绕，以及重复时间戳、倒退时间戳和关闭后的拒绝。无效版本、空指针和超限尺寸返明确错误。

macOS 的窗口探针沿用 RW03 的 ScreenCaptureKit 和 AppKit。专用构建把单窗口像素送入 WebRTC H.264，再由预览控件绘制解码输出。托管机验证红色到绿色、窗口缩放和关闭时清屏。该探针使用系统现有录屏许可，不会请求新许可。

单机传输实验建立两个 WebRTC 端点，在 `127.0.0.1` 上以 UDP 和 DTLS 传送合成视频。macOS 使用 VideoToolbox H.264，Windows 使用只提供 VP8 的 libvpx 工厂。两端检查接收帧的尺寸与亮度、关闭后停止收帧、重连的 ICE 凭据更新，以及 offer 和 answer 的指纹、ICE 凭据、媒体方向与额外媒体被替换时的拒绝。端点使用虚拟音频设备和本机生成的视频。

整链路探针把 ScreenCaptureKit 采集的测试窗口接到同一对回环端点。发送端只发视频，接收端只接视频。AppKit 从最新的解码帧绘制，测试核对绘制像素由红转绿、窗口尺寸变化和来源关闭后清屏。画面留在托管机内存，探针不打包成应用。

撤权回归在来源窗口仍打开时点「停止」，确认清屏、端点关闭和旧采集释放。探针保留旧画面及旧端点再打开同一窗口，将旧帧分别提交到已关闭的媒体端点和旧显示输出，检查拒绝后才确认新画面的像素。

回环解码和 AppKit 层共用单调时钟。一帧从接收端解码回调起保留两秒。等待取帧、像素转换和重复绘制均计入期限。测试分别检查取出帧时保留原始时间，以及 AppKit 的过期清理。

启停回归在同一托管 macOS 窗口上重复 100 次真实采集、传输及呈现。每次停止均检查 ScreenCaptureKit 回执、旧输出销毁、WebRTC 端点关闭、清屏和停止轮询。报告记录停止后的 RSS、线程和描述符数，检查预热后的描述符增长。

预览复用一个 Core Image 渲染上下文。[上下文对照](https://github.com/ForceMind/Linko/actions/runs/45065522785/artifacts/14771209787)记录了两种模式的差异。当前 Actions 在同一 runner 的独立进程分三组各运行 100 次，覆盖整链路、真实单窗口采集加本机绘制、固定合成帧经 H.264 加密回环。报告记录 RSS、物理内存占用、在用堆、分配区容量、线程及描述符。后两组只用于诊断资源变化。

完整回环的采集端用 Core Video 池复用送编 BGRA 缓冲。当前尺寸的池最多分配六个缓冲，全部占用时跳过本帧。尺寸变化时替换池，仍被编解码器持有的旧帧按系统引用生命周期释放。停止时旧采集对象释放池并拒绝继续分配。

只收帧的对照进程沿用完整回环的真实窗口、采集尺寸、像素池、加密端点和停止回执。它在同一显示轮询入口取得解码像素并立即释放，用于区分生成和展示解码图像的开销。

每个预览复用一条串行采样队列，每次屏幕采样回调有独立的自动释放作用域。停止时先关闭旧输出，等待 ScreenCaptureKit 停止回执和已排队的采样，再开放下一次选择。100 轮验证同时检查采样队列复用。

探针按 macOS 虚拟内存分配标签汇总第 10 和第 100 轮停止后的区域及映射页差值。报告只记录标签、区域数量和字节总数，共享映射可能包含同一物理页。这组差值用于定位增长类别。

完整回环在同一 runner 上分两个进程各运行 100 次。第一组只把送编前的 Core Image 裁剪切换为软件渲染，`--gpu-crop` 对照组沿用原有上下文。两组共用真实窗口、接收呈现、撤权和资源采样检查。

`--crop-only` 对真实窗口复用 GPU 裁剪及送编缓冲池，检查生成的 BGRA 缓冲尺寸和类型，随后释放。该组使用相同的采样队列、停止回执和 100 轮资源采样，采集过程中没有创建媒体端点。

`--cpu-copy` 通过固定 WebRTC 已带的 libyuv，按行间距复制真实窗口的 BGRA 内容到送编缓冲池，保留接收端呈现。开始前用有行填充和非零裁剪偏移的合成缓冲检查奇数尺寸对齐及越界拒绝。同一 runner 上与 GPU Core Image 裁剪对照各跑 100 轮。

独立媒体对照使用同一种合成 BGRA 图案。保留 224×144 的跨会话复用组，再用真实窗口只收帧组报告的送编尺寸分别跑跨会话复用和每轮重建缓冲。各组都新建媒体端点并跑 100 轮，用于区分像素尺寸和缓冲生命周期的影响。

macOS H.264 实验调用系统编解码器。Windows H.264 factory、局域网设备信令、远端窗口呈现与分发许可继续按 RW04 方案推进。产物仅包含验证报告。
