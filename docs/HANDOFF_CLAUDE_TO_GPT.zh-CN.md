## 3. 单向输入故障：诊断、修复和仍未解决的部分

### 3.1 原始症状

Windows 控制 Mac：鼠标和键盘可用，滚轮不行。Mac 控制 Windows：鼠标过不去。

### 3.2 已查明的原因和已做的修复

1. **Mac 过不去：两端方向默认都是“另一台在右”，不互补。**（已验证：用户把 Windows 设为左、Mac 设为右后 Mac→Windows 可以控制。）
   - 修复在 PR97：`LayoutHint{local,peer}`（`crates/peerglide-protocol/src/layout_ipc.rs`）在连接中检测不一致，GUI 提示并提供一键修正；GUI 端在工作进程确认前保留旧方向提议（`layout_updates.rs`）。从代码看，方向检测依赖 Acquire 里携带的边（`remote_edge == edge.opposite()`）。
2. **Windows→Mac 滚轮无效：Apple 芯片上对可变参数函数的 FFI 调用约定错误。**（已验证：用户用集成包实测，Windows 控制 Mac 的滚轮正常了。）
   - 修复在 PR99，改用 `CGEventCreateScrollWheelEvent2`。PR97 另外跳过零增量滚轮（`is_zero_scroll`）。
3. **Mac→Windows 反复中断，Windows 报 `Error: native receive service: Timeout`。** 用户最近一次实测的现象：Mac 控制 Windows 仍不正常；Mac 光标在控制期间还跟着动；Mac 这边滑滚轮也有效果；离开屏幕边缘后会断开对 Windows 的控制。
   - 从代码看，Windows 接收端的原生注入线程曾与钩子线程共用，注入阻塞会让 250ms 的命令超时，超时又被当作致命错误结束会话。已做的缓解：
     - PR100：命令超时且接收状态已在 Draining/Retired 时只结束本次控制，不断开连接（`session.rs` 的 `Recovery::input/pointer`）。
     - PR106：参照 Oink 的做法，把 Windows `SendInput` 移到独立注入线程（`crates/peerglide-platform/src/inject_thread.rs`）。有界队列 256、光标移动合并、释放栅栏（队列清空后才允许离开接收状态，`FENCE_MS` 1000ms）、失败的 Up 事件通过 `reown` 回收并保留重试次数（`RETRIES=3`）。代码评审（P1）发现重试次数在重新入队时被重置，已在 `receive_driver.rs` 的 Ledger 中修复并加了测试 `repeated_asynchronous_release_failures_stop_at_the_retry_limit`。
     - PR104：KVM-DIAG/5 增加 `slow_ptr`、`slow_inp`、`loop_stall` 三个计时计数，用于下次实测判断停滞来自哪里。
   - **这些缓解没有经过物理验证**（用户说不用再测，先做 UI）。是否真正消除 `Timeout` 和 Mac→Windows 中断，需要用 PR114 的两端包再测一次，并把两端的 `KVM-DIAG/5` 行带回来。
4. **Mac 光标在远程控制时不隐藏、仍跟着动。** PR98 加了源端光标冻结（`source_cursor.rs`，`FreezeState`，只有系统确认后才记为 owed，所有结束路径恢复，`reconcile_source_cursor`）。
   - 不确定用户最近一次实测的包是否已包含 PR98；**以实测所用 CI 运行对应的提交为准**，不要假定。
   - Oink 的完整方案（透明 AppKit 面板、私有 CGS 接口、worker 主线程运行 NSApplication）改动大且涉及私有 API，**用户没有授权**，本会话建议暂缓。要做的话先写 ADR 并征求用户同意。
5. **Mac 滚轮在远程控制时仍作用于 Mac：** 猜测与第 3 条的超时有关（控制被提前结束后事件回到本机），没有证据，需要 /5 计数确认。

### 3.3 诊断计数的约定

- 摘要格式 `KVM-DIAG/2→/3→/4→/5`，`MAX_SUMMARY_BYTES = 1600`，`is_summary` 认 `KVM-DIAG/5`。当前共 67 个计数键（`crates/peerglide-platform/src/input_diagnostics.rs`）。`[AtomicU32; N]` 超过 32 个元素后没有 `Default`，所以手写了 `impl Default`（用 `std::array::from_fn`）。
- 判读指南见 `docs/handoff/oink-input.md` 第 3 节的决策表（针对 /3，思路对 /5 同样适用）。

### 3.4 Oink 输入机制对照（只读研究）

完整报告见 `docs/handoff/oink-input.md`。要点：

- Mac 位移取法与 Oink 同源（读 CGEvent 的 MouseEventDeltaX/Y），“读错字段”不成立。
- Oink 做了而 Linko 当时没做的：Mac 光标解耦/隐藏；Windows 注入在独立线程；Windows 滚轮来源识别（驱动软件注入的滚轮）；回程判定的迟滞。其中注入线程已在 PR106 落地；光标冻结在 PR98（弱于 Oink）；其余见第 7 节待办。

## 4. UI 重做：设计思路、线稿和落地状态

设计规格原稿见 `docs/handoff/ui-spec.md`（含 Oink 动效清单 O1–B7、Linko 全部页面与文字盘点、egui 可实现性、实施切片、需要用户拍板的决策）。下面是结论和落地状态。

### 4.1 设计思路

问题：旧界面是“6 项文字导航 + 大量说明句”，两台电脑的关系要在多个页面之间跳转才能理解，主工作区里大约六成文字（导航标签、页头、画布说明、设备卡、正常状态说明、宣传句）可以用图形代替。

做法（参照 Oink 的交互结构，但全部用自己的话和自绘实现）：

1. 单窗口：可折叠设备侧栏 + 画布首页 + 标题栏状态胶囊；设置、快捷键用“返回箭头”进入子页，不再有六项文字导航。
2. 状态用“形状加颜色”表达，不单靠颜色；警告和危险状态胶囊必须同时带不超过 6 字的文字。
3. **K 类文字（授权、同意、危险操作、恢复状态、错误原因）不删语义**。可以拆短、加图标、移位置，但任何 K 类信息不能只放在悬停提示里。安全对话框只重排版，用逐条对照表验收。
4. 动效只做一次性反馈：每个动效 ≤360ms，播完不再请求重绘，空闲时零持续重绘。
5. 图标用 egui `Painter` 自绘，不引入图标字体或 SVG 依赖（避免第三方许可登记和依赖审计成本）。

文字分类（G 可图形化、S 保留但压缩、K 必须保留）与每个界面元素的归类见 `docs/handoff/ui-spec.md` 第 2.2 节。

### 4.4 与规格的偏差和已知遗留

1. M5、M6 触发条件与规格不一致（只记录，不影响预算）：M5 只看胶囊短文字变化；M6 对任一角标种类变化都弹一次。

## 5. 代码审计（26 项）

完整报告见 `docs/handoff/audit.md`（基线 `c199dcd`，只读，行号已过期，使用前先对照当前代码）。严重度和状态摘要：

- P1：F01 接收端每个运动数据报都做线程往返且按 FIFO 处理（已部分缓解：Timeout 不再致命、注入独立线程）；F02 多显示器时位置被 clamp 到 0..1，进入副屏即被判为边缘；F03 回程余量过窄（入口 0.002，回程 0.001），需要迟滞；F04 系统短暂状态变化（安全输入、锁屏）被当作永久源丢失，整个会话失败且不重连（需要 ADR）。
- P2：F05–F12（本地路由队列满取消切换、亚刻度滚轮发 0/0 [已由 PR97 处理]、两端滚轮单位未标定、映射表之外的键中止远程控制、数据报逐事件 JSON 编码未合并、回调内的 `BTreeSet` 与 `mpsc::try_send`、macOS tap 超时被当作永久丢失、Windows 把所有带注入标志的滚轮旁路）。

## 6. 版本号、打包与 Mac 签名

- 版本号：`YYYY.M.D-HHMM`，取提交时间的北京时间，由 `tools/build_version.py` 生成，通过环境变量 `LINKO_VERSION` 传入构建；测试在 `tools/test_build_version.py`。macOS 的 `CFBundleShortVersionString` 为 `YYYY.M.D`，`CFBundleVersion` 为 `YYYYMMDD.HHMM`。

- Mac 授权问题：CI 的 ad-hoc 签名每次构建都会改变 cdhash，系统隐私授权（辅助功能、输入监控）会在每次更新后失效。本机的做法是用自签名证书“Linko Local Signing”重签（designated requirement 变成“标识符 + 证书叶子”，跨版本稳定），再安装到 `/Applications`。这是本机操作，证书在用户的钥匙串里，不要删除；安装和替换应用需要用户授权。
- 用户的 Mac 上是否已替换为最新版本：未确认，以用户当面回复为准。

## 8. 工作方式提示

- 小分支、小 PR；一个 PR 一个主题；不 force push。推送前本机不能编译，所以改动要写得保守，格式要对：CJK 双宽字符会让 rustfmt 换行位置与直觉不同，本会话多次因 fmt 失败而按 CI 的 diff 重新排版（`session.rs` 的 `select!` 块内 rustfmt 不处理）。
- Clippy 以 `-D warnings` 运行：`egui::Id::new` 已弃用，用 `Id::unique`；`manual_contains` 之类的新 lint 会让 CI 失败。
- egui 0.37、GUI 最低 Rust 1.95（`AGENTS.md`）；字体许可和 notice 随发行包分发。
- 子代理使用经验：每个子代理在自己的隔离工作树里工作；遇到速率限制死掉后可以用 `SendMessage` 恢复；多个 UI 切片可以并行，但文件归属要先分清（本会话中 S1–S7 并行，最后靠“基线 PR”合并验证）。
- 在别人的工作树里改文件会被钩子拦截；用自己的本地分支基于 `origin/<分支>` 工作。
