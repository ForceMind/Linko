# Linko 远程窗口：增量技术架构

日期：2026-11-13。状态：**Proposed / 待评审，未接入运行时**。依据及固定上游提交见[研究报告](LINKO_REMOTE_WINDOW_RESEARCH_2026-11-13.zh-CN.md)，任务与放行见[实施计划](LINKO_REMOTE_WINDOW_EXECUTION_2026-11-13.zh-CN.md)。下文的接口名、限制和 ALPN 均为设计候选，不冒充现有代码。

## 1. 范围与不可破坏的约束

首期 Windows/macOS 双向：各自能作为来源或观看端；先单来源只读，再显式控制。远程窗口是来源应用的画面代理，不迁移进程、文件、账号或应用安装。

保留 Rust/eframe、MIT、最低 Rust 1.95 约束、已有身份/配对、输入 v5、唯一全局捕获生命周期、注入标记、按下/释放账本、逃生键和 watchdog。不增加第二套全局 hook，不在原生输入回调内执行网络、分配、识别或磁盘操作。

观看、控制、文本、图片、文件、窗口管理、应用音频和麦克风各自独立同意，默认关闭。保存布局不保存控制租约；重启/重连不恢复旧输入。没有任意命令、脚本或隐式远程启动应用接口。

## 2. 分层结构

```text
已有 GUI / 设备身份 / 配对 / 输入 owner
                 │
      RemoteSessionCoordinator（Rust）
        ├─ 独立 QUIC 控制会话：能力、观看同意、Surface、撤销、帧描述
        ├─ 受监督 MediaWorker：原生 libwebrtc、采集、codec、解码
        │        └─ WebRTC DTLS-SRTP 媒体（首期仅局域网直连）
        ├─ Surface/View 映射 → eframe 视图 / 平台呈现适配
        └─ InputRouter → 原输入仲裁器 → 原 v5 / 原平台注入与恢复

来源：OS window → capture → codec → RTP
观看：RTP → decode → 当前授权/几何核对 → present → 显示收据
```

媒体 worker 不发放设备信任或输入许可，也不直接注入输入。没有媒体能力的旧端仍可使用原有 KVM。媒体失败、崩溃或资源超限不能拖死 KVM 的恢复通道。

按需加载/退出媒体模块；未启用远程画面时不创建采集、编码、解码、音频或周期重绘任务。Rust 负责策略，平台 glue 仅持有本机原生资源；不为了文件夹整齐立即建立大量空 crate。

## 3. 平台适配与选型

| 层 | Windows 来源/接收 | macOS 来源/接收 | 首版边界 |
| --- | --- | --- | --- |
| 选源与采集 | Windows.Graphics.Capture；显式 picker 或选中 HWND 后 CreateForWindow | ScreenCaptureKit、SCShareableContent、单窗口 SCContentFilter | 本机用户选择、允许停止；禁止无声扩大到整屏 |
| 编码/解码 | Media Foundation + D3D11 的平台适配候选 | VideoToolbox + CVPixelBuffer/IOSurface 的适配候选 | 接入 libwebrtc codec factory，运行时检查实际硬件能力 |
| 呈现 | D3D/原生表面或受控纹理上传适配 | Metal/原生表面或受控纹理上传适配 | 先建立正确 buffer 生命周期，再优化跨进程 GPU 共享 |
| 输入 | 现有 SendInput 后端及原 owner | 现有原生捕获/Quartz 接收及原 owner | 不新增全局注入 owner；保留系统权限限制 |
| 窗口位置 | 可逆的本机窗口管理适配 | 可逆的辅助功能窗口管理适配 | 默认不隐藏、不移动来源；RW09 另行放行 |

WGC 的 frame pool 生命周期、ContentSize 和 HDR 处理按 Microsoft 文档执行；不能在归还 frame 后继续使用失效 surface。尺寸变化与 device lost 重建 buffer，不显示未初始化区域。ScreenCaptureKit 的录屏权限与控制权限分别处理；系统允许某 API 不等于该应用/启动身份已获授权。[研究报告 M1/M2/A1]

第一批目标为 Windows 11 与经实测的 macOS 版本；最低 OS 不是仅由编译宏推断。对旧系统、远程桌面会话、多 GPU、权限拒绝和不支持的捕获对象展示原因，不能回退成未经许可的整屏采集。

## 4. 媒体 worker 与 libwebrtc 准入

选择原生 libwebrtc 而不是 Electron GUI。以窄 C ABI/所有者私有 IPC 隔离 C++ 构建及崩溃风险。Bridge 只接受类型化会话/采集/codec/呈现命令，不接受网络提供的可执行路径、shell、任意文件路径或 FFI 指针。

启动进程必须来自当前应用验证过的固定包位置；校验打包清单，IPC 验证同用户和会话代次；继承句柄/共享 buffer 显式归属并在退出回收。协议长度、队列、对象数量和等待时间有上限，第三方解码器崩溃由监督器隔离。不能声称应用层检查能消除 codec 的全部攻击面。

RW04 的准入证明包括：固定上游 revision/DEPS、三平台构建策略（首期 Windows/macOS 运行）、头文件/ABI 版本、codec factories、硬件失败处理、重建、可复现包和 THIRD_PARTY 清单。WebRTC 的 API 支持自定义 codec factories，但不证明 Windows 所有 GPU 已有可直接使用的硬编码实现。[研究报告 W1/W2]

首选协商 H.264 SDR 8-bit、无 B 帧的低延迟配置；实际 profile/level/packetization-mode 以双方能力为准。首批有界软件 VP8 降级可作为经评审候选；必须如实显示实际 codec、帧率和硬件/软件路径，不能悄悄 CPU 满载或把降级结果叫 H.264。codec 无交集时只让该媒体功能失败，不替换 KVM。

首版不传透明 alpha，不做跨窗口 atlas，不支持 HDR 原样透传；采用有来源边框的普通矩形窗口。HDR 来源只有在完成验证的 SDR 色调映射后才接受，否则明确拒绝。不能以 H.264 的色度抽样能力承诺任意字号完全无损。

## 5. 控制面、媒体面、输入面分离

新增控制 ALPN 候选 `linko-remote-control/1`，使用现有实际设备证书与固定身份校验，但建立独立会话，不向旧 v5 reader 写入新媒体消息。最终名称和兼容协商必须经 ADR 审核后注册。

控制面传输：能力、选源/同意、会话 nonce、对端身份、Surface 生命周期、授权代次、几何快照、SDP/ICE、撤权、错误及显示相关元数据。新端对旧端协商失败只隐藏远程画面入口。

媒体面采用 WebRTC DTLS-SRTP。SDP 指纹、角色、ICE 会话、收发方向和 Surface 授权绑定在已认证控制会话中。DTLS 自签证书并非新的设备信任来源；替换指纹、旧 offer/answer、会话重放必须被拒绝。撤销主控制会话时结束相应媒体；不能因媒体仍活跃就继续观看。

输入仍由原 owner 及 v5 执行，不再用 DataChannel 建立第二条可绕过授权的注入路径。控制面与现有输入会话必须绑定同一真实设备对；会话切换在原输入 runtime 完成释放屏障之后才能提交。

首期只提供局域网 host candidates，不默认访问公共 STUN/TURN，不自动开放公网端口。IPv4/IPv6、多网卡与防火墙失败明确显示。未来 RW08 再审查 rendezvous、ICE/STUN/TURN 与费用/配额；信令不等于无媒体带宽，中继会消耗实际流量。此项目此前的 WAN 方案并未保证永远无中继。

## 6. 核心对象、授权和生命周期

建议类型，不是既有 wire schema：

| 对象 | 必须绑定的上下文 |
| --- | --- |
| SurfaceRef | source_device、opaque_surface_id、source_generation；本机保存 native handle/PID/进程启动标识，远端不拿 OS handle 作权限 |
| ViewGrant | source、viewer、session_nonce、surface_generation、view_epoch、范围、期限/撤销状态 |
| GeometrySnapshot | geometry_epoch、源内容 rect、物理像素、逻辑点、DPI、裁剪、旋转、内容偏移 |
| MediaBinding | media_generation、已认证会话、DTLS fingerprint、方向、track/MID/SSRC、ViewGrant |
| PresentedReceipt | 当前绑定、解码帧关联标识、几何代次、呈现提交/确认状态及本机单调时间 |
| ControlPermit | 原输入 lease + 明确整机控制同意 + 当前来源/视图/几何 + owner fence |
| WindowHandoff | transaction_id、来源实例、原坐标/状态、目标和请求代次、系统效果收据、恢复状态 |

随机 ID 不是授权。原生句柄/PID 可能重用；每次原生操作前核对窗口实例、进程启动标识、来源代次和当前上下文。关闭来源后即使新窗口拿到相同句柄，也必须重新选源。

建议会话状态：Idle → ConsentPending → Negotiating → Viewing → Suspended → Closed。Control 是另外的租约状态，不把 Viewing 自动升级为控制。权限撤销、锁屏、来源退出、控制连接失效或本机接管，必须先关相应输入门、走原账本释放，再终止或清空相关媒体状态。

## 7. 关键难点：画面、几何和输入必须指向同一代次

不通过简单“最后收到一帧”判断可以点击。尺寸、DPI、裁剪、旋转、窗口位置或来源实例变化都使旧映射失效；新几何与当前画面尚未关联时禁止输入，不能把旧坐标打到新窗口。

原生媒体桥必须把实际编码/传输帧关联到 `media_generation + track/SSRC + 扩展后的 RTP timestamp`，再与认证控制面中的几何/帧描述相配；处理 32-bit RTP timestamp 回绕、SSRC 更换、重协商、丢帧和多轨。不得依赖 `VideoFrame::id()` 自动跨网络保留；WebRTC 的头文件明确其不是接收端保证。[研究报告 W3]

描述先到或视频先到都只允许有界等待；缺失映射、过期描述或不一致尺寸不激活控制。元数据贯通尚未验证前，RW04 只能交付明确状态的只读画面，RW05 不可放行。

撤销并重新观看必须创建新媒体代次，清空 decoder/presenter/元数据等待队列。首版优先关闭旧 PeerConnection 并重新协商，避免复用旧轨道造成前一次许可的画面泄漏；仅清空 UI 纹理不够。将来复用连接需要单独证明代次隔离。

静态桌面可能没有新采集帧，WebRTC 也可能生成重复/keepalive 帧。网络保活、重复编码帧和 UI repaint 不证明来源画面仍新鲜。延续 #69 的一次性有界 source-confirmation challenge，由来源 worker 核对选定窗口、当前几何、授权和采集可用性；失败则暂停控制。该确认不能拿来伪造端到端新帧或性能成绩。

坐标始终按 View 的逆变换映射到源内容 rect：平移/缩放、黑边、旋转、Retina 与 Windows DPI 分别处理；黑边和非内容区拒绝输入。独立光标层以后再加，必须避免采集光标与本地光标重复；光标看起来跟手不代表来源应用已响应。

## 8. 控制安全与单窗口的真实边界

**捕获单窗口，不等于只能控制单窗口。** Windows SendInput 是系统输入路径，受 UIPI 等限制；通用桌面输入在 macOS 同样涉及前台焦点和本地会话。仅检查窗口矩形/焦点无法消除系统快捷键及焦点竞争带来的范围问题。[研究报告 M3；既有 #69]

第一版允许两种清楚的权限：只读窗口；或用户另行同意的“控制这台电脑”。未实现可靠隔离时 WindowOnlyControl 必须返回 Unsupported，不能给界面贴一个“仅窗口控制”标签。

每个来源交互桌面同一时刻一个控制 owner。本机物理动作优先收回，多个观看端不等于多个独立键鼠座席。切换远程设备、视图或控制路径必须先关闭旧输入并确认旧注入释放；失败保持恢复警告，不把残留按键重放到新目标。

远程窗口的普通关闭只停止代理/分享，不结束来源程序。关闭来源应用、改变窗口状态是独立的类型化动作权限；首版不提供远程 shell 或任意 app launch。标题和应用名可能含私人数据，仅在授权 UI 中临时显示，不写诊断日志。

UAC、安全桌面、受保护内容、锁屏及 Secure Input 不能靠扩大权限或关闭系统安全绕过。无法控制时维持清晰只读状态或停止，不注入等待中的历史事件。

## 9. 窗口交接事务：先显示、后考虑停放、可证实恢复

首版 SourceVisibleMirror 是默认模式。后续 RW09 再提供 SourceParkedProxy：只有平台/应用组合已证明停放后持续采集、输入可达、来源可恢复，才允许该模式。最小化、隐藏、移出屏幕、切换 Space 并不天然满足这些条件。

候选事务：

1. Prepare：冻结来源实例、几何和双方许可，记录原始位置及当前可用显示器；分配 transaction_id。
2. ReceiverReady：目标真正获得并提交首帧，当前媒体/几何绑定有效，用户可取消。
3. ParkRequested：独立允许窗口管理后，在来源执行已验证的停放策略；没有此能力就继续镜像。
4. ParkConfirmed：查询实际来源位置/状态并核对仍可采集，而不是收到命令/超时就判成功；目标确认展示与来源确认分别记录。
5. ReturnRequested / RestoreConfirmed：先结束控制并释放，再把来源移回当前有效显示器；处理原屏已拔出、负坐标和窗口比工作区大。
6. RestoreUnknown：原生调用失败/超时/权限撤销时显示“恢复未确认”，保留可重试入口与最小恢复记录；不伪造恢复成功。

同一阶段重复请求幂等；旧事务 ACK 不能提交新事务；目标先崩溃、来源先崩溃、网络分区均可终止等待。重启恢复只使用用户私有、版本化的最小窗口归属记录，重新验证进程/窗口实例，绝不依据旧 PID/句柄移动新应用。

持续运行的源端 watchdog 独立于远端和 GUI。来源机器断电时不承诺即时恢复；重启后只能对确认仍属本事务的对象恢复，并保留人工恢复路径。

自然拖窗作为显式发送的后续入口：从现有捕获生命周期发送类型化意图；使用可配置修饰键/确认，区别标题栏移动、文件拖放、普通选区、系统吸附与最大化。回调只做有界投递，不在回调里采集或操作窗口。

## 10. 弹窗、文件、音频与虚拟显示器

首版分享精确选中的 top-level。新弹窗/菜单并不自动得到观看许可；出现未获准模态对象时暂停相关控制并提示本机处理或明确扩展范围。不按同进程批量广播。窗口族需要逐平台关系证据、数量限制和明确 UI，不能静默回退成整屏视频。

文件沿现有 D 系列及 #270/#273 路径继续：文件传完、原生 drop 接受、目标应用真正接收是不同收据。默认 COPY，不在远端“成功”后自动删除来源。远程窗口拖动不是文件拖动。

音频保持关闭。日后分别授权应用/系统音频与麦克风，显示真实采集范围；Apple 文档的单窗口视频过滤不意味着单窗口音频隔离。[研究报告 A2] 不因有 WebRTC 音轨就默认录音。

Windows 虚拟屏只作为可选 IddCx 支线，驱动签名、安装/升级/卸载另行授权。macOS 非公开虚拟显示接口不进入基础版依赖。即使虚拟屏能停放窗口，也没有创造一个隔离输入座席，不能承诺来源用户与远端同时独立操作同一桌面。[研究报告 M4；既有 #69]

## 11. 多设备工作空间与移动端

RW06 沿用 #69 的 Surface/View 分离及预算：多面板观看，只有显式选定的一路控制。画布缩放/平移仅改变 View，不改变来源分辨率或 OS 屏幕拓扑。同一已授权 Surface 的多个 View 可共享解码，但不同观看许可不能共享未分区缓冲。

先验证 2 个视图，再在测量后开放 4 个；离屏暂停/低频预览，焦点全帧率。无限画布不意味着无限码率、编码会话或显存。拒绝群控广播。

RW07 的第一目标是 Android/iOS 作为电脑的观看/控制端，不承诺通用 iPhone 被控能力。原生客户端通过共享会话语义、WebRTC 媒体和现有授权接入；移动输入到既有 v5 的映射仍需实现。浏览器入口的 HTTPS、安全上下文、可信配对和控制网关另审，不能让网页直接使用任意原生 QUIC socket 或忽略证书错误。

## 12. 初始资源/性能预算与可观察性

下列是**待测目标与初始保护参数，不是已测成绩**：

- RW04：每设备对 1 个活动来源，1080p30 SDR 起步；初始视频目标码率 8 Mb/s、配置上限 12 Mb/s，先验证文字质量与真实硬编，再上 60fps/4K。
- 应用自有未编码帧队列只保留最新 1 帧，解码后待呈现队列最多 2 帧；libwebrtc/驱动内部队列单独测量，不能把外层上限当端到端上限。
- 总 worker 内存、纹理数、编码会话、像素率有预算和超限动作；预算覆盖 stride、alignment、codec reference frames 和跨进程副本。跨进程 GPU 零拷贝未测前只能写优化目标。
- 不任意丢弃已编码依赖帧。退压优先在采集/编码前发生；损坏依赖由媒体层处理、申请关键帧或重建，不将 RGBA 的 latest-frame 规则直接套到 H.264。
- LAN 初始交互目标：规定设备/网络下 input-to-photon P95 ≤ 120 ms；必须同机/高速相机等可核验测量，跨机未同步时钟不直接相减。单独报告 capture/encode/queue/transport/decode/present，RTT 不是整链路延迟。
- 同时传文件时输入恢复优先；不同连接仍竞争同一物理链路。加入应用级限速/暂停和公平性测试，不宣称 QUIC/WebRTC 自动保证相互优先级。

只记录数值、状态、代次及脱敏故障码；不记录真实按键、窗口标题、图像、剪贴板、文件内容或私钥。资源与性能门槛见实施计划，不能用计数器缺失填零。
